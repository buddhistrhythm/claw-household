# 第一性原理 Review — lifeos

> 不是找 bug（那是 code review，已做，见 git 历史）。这里把项目拆到地基，逐条质问
> **承重假设是否成立**。诚实优先——只夸不算 review。

## 0. 真正要解决的问题是什么

一个人/一个家庭的根本痛点不是「存不下」，而是 **① 录入有摩擦 → 东西根本没进系统；
② 分散在十个 App → 想不起、查不到**。把它压到最里层：

> **最深的需求 = 近零摩擦的「录入」 + 跨一切的「回忆」。**

拿这把尺子量 lifeos：我们造了一套极强的 **回忆**（存储/关系/向量/图谱/MCP），
而 **录入** 还停在 SPEC。这是本 review 最重要的结论，见 §2。

## 1. 承重假设逐条质问

### 假设 A：「统一到一个库」本身就是胜负手
**部分成立，但理由说错了。** 统一的价值常被说成「跨域 join」（如「上月在宝宝身上花了多少
+ 尿布是否要补」）。可现实里家庭 95% 是单域操作；只为那 5% 的跨域查询做统一，会输给
单域最强（Grocy 管库存、Firefly 管钱）。
**真正的回报不是跨域查询，而是：统一录入口 + 一个地方看 + 基础设施只造一遍**
（搜索/图谱/加密/镜像/MCP 全域复用）。定位要从「能 join」改成「**一处录、一处问、底座共享**」。

### 假设 B：瓶颈在「存储与检索」
**不成立——瓶颈在录入。** 一个能完美回忆但需要 `txn-add --amount-cents 4599` 的系统，
数据库会是空的。**数据只有在录入无摩擦时才存在。** 推论很硬：
**捕获/插件系统不是 Phase 3，它才是产品本体；我已造好的存储/图谱/语义/MCP 是必要的
管线，但不决定成败。** 我把容易的 80%（后端）做完了，决定生死的 20%（无摩擦录入）还是张图纸。
你问 Meta Ray-Ban 接入，方向恰好正确——那才是题眼。

### 假设 C：LLM 的价值在「带引用的检索」
**只对了一半。** LLM 最不可替代的价值在 **输入侧**：把「garage 加两箱 3 号尿布」解析成
结构化实体。我在检索侧（MCP/life_context）投入过多，输入侧（Router 解析）投入过少。
**重新配比：把 LLM 预算从「读」挪一半到「写」。**

### 假设 D：DB 主 + Obsidian 富镜像
**留着，但它是特性不是支柱。** 镜像的代价是第二真相源 + 攻击面（我们刚修了
`data.enc` 明文泄漏进 vault）。结论：镜像必须 **单向、按设计有损（永不含密文/秘密）**，
现在已强制。别把它当卖点。

### 假设 E：本地优先 / 自托管是核心
**是真差异化，但也是核心张力。** 自托管让你免于「创业公司关停带走你的数据」
（Omnivore/Pocket 之死），对财务与孩子数据尤其值。但——
**最需要统一生活捕获的人（忙碌的家长），最不可能去跑 docker-compose。**
得诚实回答 **用户到底是谁**：lifeos 现实上是「愿意自托管的技术型用户/造物者的个人系统」，
这是合法但狭窄的目标。别假装它面向所有人；否则 onboarding 就是隐形的天花板。

### 假设 F：数据模型（entities + relations + JSONB）
**站得住**（JSONB 胜裸 EAV 的论证之前已立）。但有个一阶缺口：
**缺时间/事件模型。** 生活是事件流（买入、用掉、移动、付款、换尿布），而 lifeos 的
entities 偏「当前状态」。「上月花了多少」「何时断货」需要的是 **事件日志**，不是当前态。
反而老的 household 已经在这么想（consumption_history、baby_log）。
**洞见：lifeos 应更「事件溯源」——库存量 = fold(进/出事件)，而非一个可变字段。**
append-only `capture` inbox 是个开头，但领域事件（txn 是事件、consume 是事件）值得一等公民化。

### 假设 G：范围与身份
仓库里现在有三样重叠的东西：老 `household`（JSON 文件 + 网页）、`rsspool`（RSS→库）、
新 `lifeos`（统一 Postgres）。**最大战略风险：lifeos 变成第三个 silo，而不是统一者**——
对一个「统一」项目是莫大讽刺。判据很简单：
**household 的 JSON 是否迁上 lifeos？rsspool 是否真用 lifeos 的库（目前只搬了 ingest 逻辑）？**
不迁移，统一只是 PPT。这是 #1 要回答的问题。

### 假设 H：MCP/agentic 是回忆接口
那 **主 UX 脊柱** 是什么？现在有三个入口在隐性竞争：网页 App、聊天/MCP、边缘捕获。
应明确为：**边缘捕获录入 → 聊天/MCP 回忆 → 网页只做复核/确认**。否则三个半成品界面互相拆台。

## 2. 把结论压成一句

> **我建好了「回忆」的引擎，但「生活 OS」的胜负在「录入」与「迁移」。**
> 存储是管线，捕获才是产品；统一不靠 schema，靠 household/rsspool 真的搬进来。

## 3. 品味缺口：那个还差一半的统一抽象

已做到的优雅：type 即扩展（不改表）、relation 一等公民、加密拆分、规则优先于 LLM、
捕获即「再加一个 Source」。这些是真有品味的。

**未收口的优雅**：一个领域现在要在四处分别登记——`types`（已聚合）、cli 命令（手写
switch）、未来的 router `intents`、MCP 工具。它们应来自 **同一份领域清单**：

```js
// 设想：每个 domain 只声明一次，cli / router / mcp / obsidian 全部消费它
module.exports.manifest = (store) => ({
  types:    [...],          // entity_types 注册
  commands: { 'txn-add': {...} },   // cli 自动发现
  intents:  [ Intent ],     // 捕获 Router 的可路由目标 + LLM tool-use schema
  mcpTools: [ ... ],        // MCP 自动暴露
});
```

cli 的 40+ case switch、types 聚合、mcp 工具、router 目标——**全部由 manifest 派生**。
这才是让整个系统「咔哒一声扣上」的那个抽象。我只做了 types 聚合那一半；补完
manifest 是品味的真正兑现，也顺带消灭 cli 的样板。

## 4. 据此的优先级（替代原 SPEC 的分期）

1. **回答迁移问题**（household JSON → lifeos entities 的导入器；rsspool 直连 lifeos 库）。
   不解决，统一性是假的。
2. **捕获 P0 落地**（Source→Capture→规则 Router→`storage.add_item`→`pending` 确认）——
   把「产品本体」从图纸变成能跑的最小闭环。
3. **领域 manifest 抽象**收口（cli/router/mcp 由一份声明派生）。
4. **事件模型**：把 consume/txn/diaper 显式建成事件，状态由 fold 导出（先从库存量做起）。
5. 之后才是把 LLM router、vision、IM/眼镜 Source 接上（P1/P2），以及 MCP 的 HTTP 常驻硬化。

## 5. 诚实的非差异化（避免自我欺骗）

- 自托管本身人人都有（Firefly/Grocy/HomeBox 都能）。
- 单域深度打不过专用品（预算不如 Firefly、备餐不如 Grocy）。
- UX 打磨、多端同步：目前都是弱项，且不该去硬拼。
  **靠的是「广度 + 关系 + 所有权」，不是任一竖井里的深度——这点要敢于明说与取舍。**
